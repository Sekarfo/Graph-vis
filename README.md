# Визуализация графа ВОЛС — по областям

Интерактивный вьюер плана строительства: `index.html` + `graph-app.js`.
Графов несколько (по областям), каждый — отдельный файл `regions/<slug>.json`;
какой открыт — решает URL-параметр `?graph=<slug>`.

**Работаете над своей областью или правите чужую?** → [CONTRIBUTING.md](CONTRIBUTING.md)
— как несколько человек добавляют/правят области параллельно без конфликтов
в git, локальный вьюер с правками, что коммитить и как деплой подхватывает
новые области сам.

- **Фронт**: селектор области в шапке (появляется, когда сервер отдаёт
  `GET /api/graphs` и графов ≥ 2); прямые ссылки — `index.html?graph=almaty-zhetysu`.
  Без параметра открывается жамбылский граф — все старые ссылки живы.
- **API**: каждый эндпоинт (`/api/progress`, `/api/smr`, все `/api/graph/*`)
  принимает `?graph=<slug>`; без него работает дефолтный граф. Файл графа —
  `GET /regions/<slug>.json` (легаси-путь `/zhambyl-graph.json` сохранён —
  им пользуется бот, см. `app/config.py: graph_path` в основном репозитории).
- **Правки** независимы по графам (свой файл, свой лок, свой кэш прогресса);
  id новых узлов получают префикс графа (`N…` — Жамбыл, `A…` — Алматинская+Жетісу),
  чтобы привязка `graph_from_node`/`graph_to_node` от бота не могла указать
  на узел чужого графа. `idPrefix` каждой области обязан быть уникален —
  `scripts/validate_region.py` проверяет это перед коммитом. **Занятой буквы
  недостаточно сменить в `meta.registry`**: id уже созданных узлов остаются со
  старой, и пересечение никуда не денется — валидатор ловит и это, а чинит
  `scripts/repair_id_prefix.py <slug> <буква>` (переписывает префикс во всех
  ссылках файла и пересобирает fallback). Буквы `E` и `X` узлам недоступны:
  с них начинаются id рёбер и псевдоузлов внешних связей.
- **Прогресс**: push от бота один на всех (полный снимок строк);
  жамбылский граф получает все строки (как раньше), остальные — только строки
  своей области (по привязке от бота либо совместимости района отчёта с
  районами графа — иначе сёла-тёзки утаскивали бы км в чужую область).
- **Добавить область**: `python scripts/new_region.py <slug> "<Название>"` —
  создаёт `regions/<slug>.json` с уникальным `idPrefix` автоматически. Дальше
  файл сразу подхватывается сервером, `Dockerfile` копирует всю папку
  `regions/` целиком — деплой ничего не нужно править. Подробности —
  [CONTRIBUTING.md](CONTRIBUTING.md).
- **Fallback для file://**: `regions/<slug>.fallback.js`
  (`window.GRAPH_DATA_BY_SLUG[slug]`), подключается фронтом динамически,
  одинаково для всех графов включая дефолтный.

### Оцифровка `regions/almaty-zhetysu.json` — как и что проверено

Данные извлечены векторной экстракцией из PDF (PyMuPDF: подписи со
координатами + пути ВОЛС с цветом/пунктиром/толщиной — та же классификация
цветов, что в легенде чертежа), не «на глаз». Проверено:

- **Районы** — 20 районов через flood-fill отсеков между границами
  (штрих-пунктирные барьеры чертежа): 0 утечек между отсеками, 0 узлов вне
  отсеков после калибровки. Точечно сверено по PDF: Хоргос/Чунджа/Нарынкол/
  Каратал и др. — район/область совпадают.
- **Внешние связи** (5 шт., переход в Жамбылскую область) сверены по km
  с зеркальными записями в `regions/zhambyl.json` — совпадают (например, 93.4 км
  Каншенгель↔Аксуйек с обеих сторон).
- **Визуальная сверка** нескольких районов (растр PDF vs рендер JSON) —
  топология, названия и км-подписи совпадают.

Известные пробелы (не критично — правятся через «✏️ Правка» в вьюере, как
любые данные графа):

- ~15% рёбер новой области (149 из 967) не получили `lengthKm` — подпись
  «N км» на чертеже стоит слишком далеко от линии для автоматической
  привязки. Такое ребро просто рисуется без дроби «X/Y км», как и 9 таких
  рёбер в исходном жамбылском графе.
- 11 узлов (АТС/ATN) без имени — на самом чертеже эти значки не подписаны
  отдельно (либо подпись однозначно относится к соседнему объекту).
- В отчёте экстракции (`build_edges.py` в scratch) остаётся ~37 «висячих»
  обрывов линий — на практике это дублирующиеся короткие хвосты одного и того
  же соединения на чертеже (проверено точечно: сама связь между узлами при
  этом уже создана из другого сегмента той же линии), не потерянная топология.

### Оцифровка `regions/kyzylorda.json` — как и что проверено

Векторная экстракция из `data/Кызылординская.pdf` (PyMuPDF): значки узлов
опознаются по цвету заливки/обводки из легенды чертежа, линии ВОЛС — по пяти
цветам легенды (синий — существующая, янтарный — по проекту, фиолетовый — вне
проекта, красный — без свободных ОВ, оливковый — большей ёмкости).

**Значок, стоящий НА линии, вшит в неё, а не лежит сверху.** Каждый отрезок
чертежа физически разрезается границами значков, куски между соседними
значками и становятся рёбрами; примыкания «отвод — магистраль» (тройники без
своего значка) вливаются в ближайший значок, а стопка АТС+ATN+OLT считается
одной площадкой — линия, пришедшая в любой её значок, приходит на площадку.
Проверено скриптом: **0 значков, которых касается линия ВОЛС, но которые
остались без ребра**; граф — **одна связная компонента** (158 узлов из 218,
остальные не подключены и на чертеже: 22 СНП «Спутник», OLT-значки в стопках
и «Комекбаева»).

**Извилистых линий OLT/АТС здесь нет намеренно** — по просьбе заказчика голубые
PON-ветки и зелёные аплинки с чертежа не переносились. Сам вьюер их не
достраивает (см. «Извилистые линии OLT/АТС»), так что слой остаётся пустым.

Известные пробелы (правятся через «✏️ Правка», как любые данные графа):

- 25 рёбер из 166 без `lengthKm` — на чертеже у них нет подписи длины (обычно
  это короткий отвод от села до магистрали).
- Подписи вида «Бирлестик – Шокай – 12 км» описывают участок из нескольких
  рёбер; там, где известны все длины кроме одной, остаток вычислен вычитанием
  (2 ребра: `E0003` 9.1 км, `E0014` 53.679 км).
- «Комекбаева» (СНП вне проекта) стоит с подписью «60км», но линии к ней на
  чертеже не нарисовано — узел остался без связи.

### Оцифровка `regions/karaganda-ulytau.json` — как и что проверено

Векторная экстракция из `data/Карагандинская, Улытауская.pdf` (PyMuPDF), тот
же метод и та же легенда цветов, что для Кызылординской области — но страница
обычного A4-масштаба с гораздо более мелкой графикой (значок ~2-5pt вместо
~15-35pt), поэтому все геометрические допуски свои, откалиброваны по фактическому
замеру, а не взяты из Кызылординского скрипта как есть.

**Значок, стоящий НА линии, вшит в неё, а не лежит сверху** — тот же принцип,
что в Кызылординской области (см. выше). Проверено скриптом: из 465 значков,
которых физически касается линия ВОЛС, **462 получили ребро** (3 остались
недошитыми — плотный узел, где значок с линией стоят ближе допуска соседнего
значка; правится через «✏️ Правка»); граф — **одна связная компонента**
(454 узла из 597; остальные не подключены и на чертеже: 44 СНП «Спутник»,
OLT-значки в стопках, несколько «пока без трассы» плановых точек).

Два содержательных отличия от Кызылординской области:

- **Районы — не полосы, а разбросанные многоугольники.** Один район на этом
  чертеже подписан по 2-5 раз в разных, не граничащих друг с другом местах
  (например, «Осакаровский район» — 3 раза). Вместо сравнения x с порогами
  (как в Кызылординской области) `district_for()` берёт **ближайшую по
  расстоянию** подпись «... район» — 23 подписи, 9 уникальных названий.
- **Значок DWDM** здесь настолько дробный (десятки микро-штрихов на значок),
  что векторная реконструкция контура ненадёжна — вместо этого он ловится по
  надписи «DWDM» рядом (4 шт., все — netengine/planned).
- **Координаты x/y домножены на 7** при записи в JSON. Исходный чертёж — A4
  (595×842pt), значки на нём мельче в ~7 раз, чем в остальных областях
  (которые оцифрованы с чертежей в разы крупнее физически); вьюер рисует
  значки ФИКСИРОВАННОГО размера в пикселях (`nodeRadius()` в `graph-app.js`),
  так что без домножения соседние узлы на этой площадке были бы теснее, чем
  сами значки, и накладывались бы друг на друга. Домножение — чисто
  раскладочная правка (x/y — условные единицы редактора, см.
  CONTRIBUTING.md), на км/топологию не влияет; после него медианное
  расстояние до ближайшего узла (40.1) — того же порядка, что у остальных
  областей (40-80).

Известные пробелы (правятся через «✏️ Правка», как любые данные графа):

- 46 рёбер из 459 без `lengthKm` — на чертеже у них нет подписи длины.
- На этом чертеже нет подписей вида «А – Б – N км» (участок из нескольких
  рёбер одной надписью) — только «N км» на каждый сегмент по отдельности,
  так что вычислять длину остатком (как в Кызылординской области) было не из
  чего.
- 3 значка (из 465, которых касается линия) остались без ребра — не хватило
  геометрического допуска в очень плотных узлах (несколько значков ближе
  0.5pt друг к другу); физически видно в PDF, что связь есть.

## Как открыть

**Вариант 1 (просто):** двойной клик по `index.html` — страница возьмёт данные из
`regions/<slug>.fallback.js` (fallback для `file://`; только просмотр, без правки).

**Вариант 2 (сервер, нужен для правки):**

```bash
cd graph-vis
pip install -r requirements.txt
uvicorn server:app --reload
# → http://localhost:8000
```

Если `regions/<slug>.json` обновился не через UI (правили руками/скриптом) —
перегенерировать fallback:

```bash
python scripts/build_fallback.py               # все regions/*.json
python scripts/build_fallback.py regions/zhambyl.json   # один файл
```

## Возможности

- **Пан/зум** — перетаскивание мышью, колесо, двойной клик; кнопка «Вписать».
- **Клик по узлу** — панель с деталями (район, подключения, objectId) и списком
  всех связей с длинами и прогрессом; клик по связи ведёт к соседнему узлу.
- **Фильтры** — район, муфты вкл/выкл, существующие/плановые ВОЛС.
- **Модерация отчётов бота** — панель «🐞 Отчёты»: применить отчёт на граф или
  убрать совсем (см. «Прогресс строительства»).
- **PON/аплинки** — извилистые линии как на чертеже: голубые (#00B0F0) —
  PON-ветки от OLT к обслуживаемым СНП, зелёные (#00B050) — аплинк от
  существующей ATN к OLT. Рисуются только те, что нарисованы руками
  (автодостройки по топологии нет), отключаются галочкой «PON/аплинки». Логики
  не несут (в км и прогресс не входят) — см. «Извилистые линии OLT/АТС».
- **Поиск с нечётким сопоставлением каз/рус** (см. ниже).
- **Тема** — светлая/тёмная (кнопка ◐ или системная).

## Прогресс строительства (линия = прогресс-бар)

Выполненная часть сегмента рисуется сплошной зелёной линией поверх плановой
(пунктирной), с подписью `1.5/3 км`, заливка идёт со стороны, откуда строят
(`fillFrom`).

Прогресс-бар **один на все источники факта** — сервер сводит их в `doneKm`
ещё до отдачи фронту (`_build_progress` в `server.py`). Источников два:

1. **Свод СМР** — книга «Отчет СОИ», лист «СМР» (см. следующий раздел). Ложится
   на бар сразу, без всяких условий.
2. **Отчёты бота** — только те, что **применены в очереди модерации** (см. ниже).

Если оба попали на одно ребро, берётся **большее**, а не сумма: оба числа
описывают один и тот же физический участок, и сложение посчитало бы одни и те
же километры дважды.

Помимо API прогресс можно задать статикой: файл `progress.json` рядом с
`index.html` или поля `doneKm` / `progress` прямо на ребре в `regions/<slug>.json`:

```json
{
  "edges": { "E0000": { "doneKm": 2.5 }, "E0281": { "progress": 0.4 } }
}
```

### Модерация отчётов бота (🐞 Отчёты)

Push от бота присылает **полный снимок** — все отчёты, и старые и новые, — а
привязка отчёта к участку получена фаззи-поиском по названиям и иногда
промахивается. Поэтому отчёты бота на прогресс-бар сами по себе не попадают:
они выстраиваются в очередь в панели «🐞 Отчёты», где у каждого видно, на какое
ребро он ляжет, и две кнопки:

* **✓ Применить** — километры отчёта ложатся на граф (кнопки нет у отчёта без
  привязки: применять там нечего, сперва надо чинить привязку);
* **✕ Отменить** — отчёт убирается насовсем: исчезает из очереди и с графа;
* **↩ Вернуть** — у уже применённого: снять с графа и вернуть в очередь.

Решение принимает `POST /api/graph/moderate-report` и хранит в
`DATA_DIR/progress-moderation.json` по id отчёта — оно переживает рестарт и
следующий push, иначе разбор очереди пришлось бы повторять каждые 5 минут.
Эндпоинт лежит под `/api/graph/*` и потому закрыт тем же паролем правки
(`EDIT_PASSWORD`): менять картинку прогресса для всех, кто смотрит вьюер, —
такая же правка, как переименовать узел.

## Факт по своду СМР («Отчет СОИ»)

Основной источник факта на прогресс-баре: книга `data/Отчет СОИ*.xlsx`,
лист **«СМР»** — то, что подрядчики показывают в отчётности. Рисуется штатным
прогресс-баром, тем же зелёным, что и применённые отчёты бота, — отдельного
слоя, цвета или переключателя нет.

### Почему доля, а не километры

Свод даёт факт **на село целиком** (магистральная трубка, задувка ВОЛС), а не
по сегментам чертежа: строка «с.Алгабас — план 10.9 км» покрывает и общий
ствол ветки, на котором висят ещё три соседа. Разложить эти километры по
конкретным рёбрам нечем — получилось бы враньё с точностью до сегмента.
Поэтому на карту переносится процент выполнения села, и закрашивается его
собственная **ветка**: только те плановые линии, что ближе к нему, чем к
любому другому селу (`attribute_edges_to_snp` в `progress_core.py`). Ветки
не пересекаются, поэтому общий ствол не красится по разу за каждое село.

Доля больше 100 % обрезается: факт трубки регулярно превышает план свода —
свод считает трассу до НП, а трубку кладут и по распредсети внутри села.

На прогресс-бар доля попадает километрами (`доля × длина сегмента`), поэтому
подпись `1.5/3 км` на линии и плитка «Выполнено» читаются так же, как раньше.

### Обновить свод

```bash
# положите новую книгу в data/ и соберите выгрузку заново
python scripts/import_smr.py              # берёт свежий data/Отчет СОИ*.xlsx
python scripts/import_smr.py --report-only # только сверка, без записи файлов
```

Скрипт кладёт `smr/<slug>.json` — их читает сервер, подмешивая свод в
`/api/progress`; отдельный `GET /api/smr?graph=<slug>` отдаёт ту же раскладку
сырьём (план и факт по каждому селу, доля по рёбрам) — он нужен для разбора
цифр, фронт его не запрашивает. Ещё скрипт пишет **`SMR_RECONCILE.md`** —
сверку свода с графами: сёла свода, которых нет в графе; СНП графа, которых
нет в своде; и расхождение плановых км свода с длинами веток чертежа по
каждому селу. Это рабочий список того, что надо поправить в оцифровке.

Файлы `smr/` коммитятся и попадают в образ (`Dockerfile`), в DATA_DIR-volume
их нет: это выгрузка из внешней книги, а не то, что правят через вьюер. Нет
файла области — свод просто не подмешивается в прогресс, всё остальное
работает; через `file://` (без `server.py`) его тоже нет, как и живого
прогресса вообще.

## Факт по своду «СНП 2.0» (по конкретным рёбрам)

Второй слой факта, независимый от «Отчёта СОИ» выше. В отличие от него км
ложатся не долей на всю ветку, а на КОНКРЕТНЫЕ рёбра маршрута: свод описывает
его цепочкой участков (метка → км → метка → … → НП), и эта цепочка сопоставляется
с графом. Метрики две и они не складываются — трубку прокладывают, ВОЛС в неё
задувают, поэтому на фронте это переключатель «Прогресс», а не одна цифра.

```bash
python scripts/import_smr2.py --region all --from-sheet   # из живой Google-таблицы
python scripts/import_smr2.py --region zhambyl            # из книги в data/
python scripts/import_smr2.py --region zhambyl --report-only
```

Скрипт пишет `smr2/<slug>.json` (его отдаёт `GET /api/smr2`) и два отчёта:

* **`SMR2_RECONCILE.md`** — рабочая сверка по каждой области: что не привязалось,
  где длина графа не сходится со сводом, куда ушёл каждый километр факта (баланс
  должен сойтись с итогом свода) и на каких участках чертежа не проставлена
  длина, которую свод как раз знает (раздел 7 — прямой список правок чертежа);
* **`SVOD_ISSUES.md`** — сводный по ВСЕМ областям список вопросов к самой книге,
  чтобы отдать его тем, кто её ведёт: похожее на описку, расхождения свода с
  чертежом, строки с фактом больше плана и то, что не удалось разобрать. Наших
  собственных промахов привязки там нет — только то, что чинится в своде.

Столбцы ищутся по ЗАГОЛОВКАМ, а не по номерам: книгу правят руками, и она
уже ездила — вставили три столбца, итог трубки переехал с `WQ` на `WT`, и по
старым индексам читалась бы соседняя пустая колонка.

**Цифра свода кладётся на маршрут как есть.** Факт регулярно больше плана
строки (свод считает трассу до НП, а трубку кладут и по распредсети внутри
села, и участок сдают, не разнеся по строкам) — но решать за составителей
свода, какие километры «настоящие», не наша задача: мы цифру получаем и
показываем. Единственный предел — геометрия: длиннее самого маршрута уложить
некуда, и неуместившееся видно в балансе строкой «маршрут короче факта», а
сами такие сёла — в разделе 4 сверки.

### Автообновление два раза в сутки

`.github/workflows/smr2-sync.yml` в 07:10 и 19:10 по Астане делает два шага в
одной джобе: сперва **забирает графы с прода** (`scripts/export_regions.py` —
см. [«regions/ — зеркало прода»](#regions--зеркало-прода-а-не-рабочая-копия)),
затем скачивает таблицу, пересобирает все области по уже свежей геометрии и
коммитит `regions/`, `smr2/`, `SMR2_RECONCILE.md` и `SVOD_ISSUES.md`. Railway
разворачивает новый образ по push в `main` — отдельный деплой не нужен.
Запустить вручную — вкладка Actions, кнопка **Run workflow** (так же увозят в
репозиторий только что сделанную правку графа, не дожидаясь расписания).

Порядок шагов не переставлять: факт ключуется id рёбер, и у перерисованного во
вьюере ребра id ДРУГОЙ — разбор свода обязан видеть геометрию уже с прода.
Экспорт и разбор живут в одной джобе по той же причине: пуш, сделанный от
`GITHUB_TOKEN`, не запускает другие workflow, поэтому отдельная джоба-экспортёр
закоммитила бы графы, но пересборку факта по ним не завела бы.

Если область развалилась (поехала шапка листа, обрушилась привязка, план
прыгнул больше чем на четверть), её файл **не перезаписывается** — на карте
остаётся прежняя версия, остальные области обновляются, а запуск краснеет
(см. `suspicious()` в скрипте). Пороги грубые — они ловят поломку разбора,
а не обычное движение факта. Исключение — правка графа: если старый файл
ссылается на рёбра, которых в графе уже нет, просадка объясняется самой
правкой, и файл перезаписывается, иначе на карте навсегда осталась бы
раскладка по удалённым рёбрам.

Ручной коммит в `regions/**` (новая область, переномерация id — только они там
и бывают, см. правила зеркала) запускает ту же пересборку сразу, не дожидаясь
расписания: геометрия сменилась, факт должен лечь на новые id.

### Сверка: всё ли, что должно быть на карте, на ней есть

Раскладка ссылается на рёбра по id, а граф правят руками — удалённое или
перерисованное ребро унесло бы запись с карты молча (фронт неизвестный id
пропускает). Поэтому каждый прогон заканчивается прямым проходом по всем
записям всех областей, включая те, что в этот раз не обновлялись:

```
python scripts/import_smr2.py --verify-only          # только сверка, ничего не тянет
python scripts/import_smr2.py --verify-only --region zhambyl
```

Прогон краснеет, если раскладка ссылается на несуществующее ребро, ребро
заливается от чужого узла, закрашено сверх длины, не сходится баланс км или
село с живым фактом перестало показываться. Остальное (сёла без привязки,
сёла, чей зачёт ушёл соседу по трассе) — в лог и в раздел «Сверка целостности»
файла `SMR2_RECONCILE.md`.

## Живое обновление (server.py)

Браузер не умеет ходить в Postgres напрямую, поэтому между данными и фронтом
стоит маленький API (`server.py`, FastAPI). Прогресс он берёт из двух
источников, по приоритету:

**1. Push от бота (основной).** Postgres живёт на сервере бота, который не
принимает входящих соединений — задеплоенный на Railway вьюер до БД не
достучится. Поэтому бот сам присылает полный снимок строк прогресса на
`POST /api/progress/push` (заголовок `X-Push-Key`, общий секрет): сразу после
подтверждения или правки отчёта плюс фоновым циклом раз в 5 минут (см.
`app/services/graphvis.py` в репозитории бота). Снимок хранится в памяти и в
`DATA_DIR/progress-rows.json` — с volume на Railway переживает рестарты.

```
Telegram-бот ──▶ PostgreSQL (сервер бота, только localhost)
      │
      └── POST /api/progress/push ──▶ server.py (Railway: вьюер + /api/progress)
                                             ▲
                                   браузер: поллинг раз в 30 сек
```

**2. Прямой SQL из PostgreSQL** — как раньше: если задан `DATABASE_URL` и БД
достижима (запуск на той же машине, где база). Используется, только пока не
пришёл ни один push.

Запуск:

```bash
cd graph-vis
pip install -r requirements.txt
export PUSH_KEY=<секрет, тот же что GRAPHVIS_PUSH_KEY у бота>
# export DATABASE_URL=postgresql://user:pass@host:5432/db  # только для запуска рядом с БД
uvicorn server:app --host 0.0.0.0 --port 8080
# → http://<хост>:8080  (вьюер) и /api/progress, /api/health
```

Либо Docker: `docker build -t graph-viewer . && docker run -p 8080:8080 -e DATABASE_URL=... graph-viewer`

### Деплой на Railway

Репозиторий содержит `Dockerfile` и `railway.json` — Railway подхватывает их
автоматически, отдельной настройки билда не нужно.

**Чеклист перед пушем** (всё это — то, на чём деплой ломается молча):

```bash
python scripts/validate_region.py     # 0 ошибок: схема, уникальные idPrefix и id узлов
python scripts/build_fallback.py      # regions/*.fallback.js в ногу с JSON
python scripts/import_smr.py          # smr/*.json из свежей книги «Отчет СОИ»
python -m pytest ../tests/test_graph_progress.py ../tests/test_smr_layer.py -q
git status --short                    # НИ ОДНОГО «??» в regions/ и smr/
```

Последняя строчка — не формальность: `regions/` и `smr/` копируются в образ
целиком (`COPY regions/ ./regions/`, `COPY smr/ ./smr/`), поэтому файл, забытый
неотслеженным в git, просто не доедет до продакшена, а сервер молча покажет
на одну область меньше.

1. **New Project → Deploy from GitHub repo** → выбрать `Sekarfo/Graph-vis`.
2. **Variables**: `PUSH_KEY` — общий секрет с ботом (у него это
   `GRAPHVIS_PUSH_KEY`; без переменной действует дефолт из кода — для боевого
   деплоя задайте свой); `DATABASE_URL` больше не нужен (БД на сервере бота
   недоступна снаружи — данные присылает сам бот, см. выше); опционально
   `EDIT_PASSWORD` и/или `READ_ONLY=1` для публичной ссылки. Порт слушать
   не нужно задавать — Railway сам прокидывает `PORT`, сервер его подхватывает.
3. **Volume** — обязательно, без исключений, потому что источник правды по
   геометрии — фронт (см. [«regions/ — зеркало прода»](#regions--зеркало-прода-а-не-рабочая-копия)):
   Settings → Volumes → добавить том с mount path `/data`, затем задать
   переменную `DATA_DIR=/data`. Без этого шага правки графа (кнопка
   «✏️ Правка») пропадают при каждом следующем деплое — контейнер стартует с
   нуля из образа, а деплой случается на каждый коммит в `main`, то есть
   дважды в сутки от джобы свода. Проверить, что том подхвачен, можно снаружи:
   `GET /progress-rows.json` должен отвечать **404** — снимок прогресса ушёл в
   том; ответ **200** значит, что `DATA_DIR` не задан, файл лежит в папке
   приложения и его раздаёт статика (заодно публично). При первом запуске том
   пустой, сервер сам
   скопирует туда все `regions/*.json` из образа (см. `discover_graphs()`
   в `server.py`); дальше все правки читаются/пишутся уже из тома, и именно
   их отдаёт `/regions/<slug>.json` — а не файлы из образа (уже существующие
   в томе файлы не перезаписываются, так что новый деплой с новыми областями
   в `regions/` докопирует только недостающее). Присланный ботом
   снимок прогресса (`progress-rows.json`) тоже лежит в томе — после
   передеплоя прогресс виден сразу, не дожидаясь следующего push (бот в любом
   случае повторяет его раз в 5 минут).
4. Healthcheck в `railway.json` указывает на `/` (всегда 200), а не на
   `/api/health` — тот честно отвечает 503, пока не настроен `DATABASE_URL`,
   и Railway бы считал деплой нездоровым до подключения БД.

Защита правки для публичных ссылок (тоннель и т.п. — на `/api/graph/*` иначе
нет вообще никакой авторизации): `EDIT_PASSWORD=<пароль>` — при первом же 401
от `/api/graph/*` фронт спросит пароль, обменяет его на токен сессии через
`POST /api/graph/login` (12 часов, с блокировкой после 5 неверных попыток) и
дальше будет слать токен заголовком `X-Edit-Token`; `READ_ONLY=1` — правка
отключена совсем, даже с верным паролем. Ни один флаг не задан — правка
открыта всем (локальный/доверенный запуск).

Как считается прогресс (`progress_core.py`, тестируется без БД):

1. Берутся отчёты `work_reports` (кроме `rejected`) с километровыми показателями;
   приоритет: задувка ВОК → микротрубка ПЭТ → траншея.
2. «Откуда» (`direction_from`) и «куда» (`settlement_name`) резолвятся нечётким
   поиском по узлам графа (порог 60/100, бонусы за СНП и совпадение района).
3. Строится кратчайший маршрут по графу, км укладываются по рёбрам
   последовательно от «откуда» — как физически идёт стройка.
4. Если «откуда» не указано, а у села ровно одна плановая линия — км ложатся на неё.
5. Всё, что не привязалось (село не найдено, маршрута нет, факт превысил план),
   попадает в `unmatched` ответа API — фронт показывает счётчик «без привязки»
   и пишет детали в консоль браузера.

«Новая запись появилась» отслеживается дёшево: API при каждом запросе сверяет
`max(id)`/`count` по таблицам (миллисекунды) и пересчитывает привязку только
если данные изменились; ответ кэшируется на 10 сек, так что хоть 50 открытых
вкладок нагрузки на Postgres не создадут.

## Сопоставление названий сёл (каз ↔ рус)

Поиск устойчив к разнице алфавитов и опечаткам: «Костобе» находит «Қостөбе»,
«Женис» → «Жеңіс», «Ауликоль» → «Әулиекөл». Алгоритм (`window.snpMatcher` в
`graph-app.js`):

1. нижний регистр, отбрасывание префиксов «с.», «ст.», «рзд.», «АТС», «СНП» и т.п.;
2. транслитерация казахских букв к русским: ә→а, ғ→г, қ→к, ң→н, ө→о, ұ/ү→у, і→и, һ→х;
3. точное совпадение / префикс / вхождение, иначе расстояние Левенштейна
   (порог схожести ~45/100).

Тот же алгоритм нужно будет портировать в Python-часть бота, когда репорты
начнут привязываться к рёбрам графа автоматически.

## Редактирование графа с фронта (✏️ Правка)

### `regions/` — зеркало прода, а не рабочая копия

**Источник правды по геометрии — фронт.** Граф правят кнопкой «✏️ Правка» во
вьюере; сервер пишет правку в свой `DATA_DIR/regions/<slug>.json`, а в
репозиторий её привозит шаг экспорта джобы свода
(`scripts/export_regions.py`, дважды в сутки и по кнопке Run workflow).

Отсюда два правила, оба выстраданы:

1. **Том на Railway обязателен** (`DATA_DIR=/data`, см. [Деплой](#деплой-на-railway)).
   Без него `DATA_DIR` равен папке приложения, правки лежат в контейнере и
   пропадают на следующем деплое — а деплой случается на каждый коммит в `main`,
   то есть дважды в сутки от самой джобы свода. Проверка, что том подхвачен:
   `GET /progress-rows.json` должен отвечать **404** (если 200 — файл лежит в
   образе рядом с кодом, тома нет).
2. **`regions/*.json` руками в репозитории не правят.** На прод такая правка не
   доедет (`discover_graphs()` копирует из образа только ОТСУТСТВУЮЩИЕ файлы),
   а следующий экспорт затрёт её состоянием прода. Пуш с ручной правкой ловит
   `.github/workflows/regions-guard.yml` и краснеет.

Законные исключения — структурные операции, которых на фронте нет: новая
область (`scripts/new_region.py`), переномерация id
(`scripts/repair_id_prefix.py`), спасение состояния прода в git. Для них
добавьте в сообщение коммита маркер `[regions-ok]`, и не забудьте, что
существующий файл области с тома всё равно не перезапишется: сначала уберите
его в томе (или пересоздайте том), иначе прод останется на прежней версии.

Забрать правки с прода вручную:

```bash
python scripts/export_regions.py --dry-run     # что изменилось бы
python scripts/export_regions.py               # забрать и перегенерировать fallback
python scripts/export_regions.py --base-url http://127.0.0.1:8000   # с локального server.py
```

Скрипт не берёт файл на веру: проверяет схему (`schema.validate_graph`),
совпадение `meta.registry.slug` с именем файла, сходимость счётчиков с
`/api/graphs` и что граф не «усох» больше чем на 5% (`MAX_SHRINK`). Не прошедшую
проверку область он не пишет, остальные забирает и возвращает код 1 — джоба
краснеет, данные не портятся.

Кнопка **«✏️ Правка»** в шапке включает режим редактирования:

- клик по **селу/объекту** → в панели справа появляются поля «Название» и
  (для СНП) «Подключений по плану»;
- клик по **линии** → поле «Плановая длина, км» (пустое = длина не задана);
- «💾 Сохранить» → изменение уходит `POST /api/graph/edit` и **автоматически
  сохраняется в `regions/<slug>.json`** (плюс синхронно перегенерируется
  `regions/<slug>.fallback.js`, пересчитываются итоги `totalKm`/`plannedKm`
  и сбрасывается кэш `/api/progress`, чтобы привязка отчётов сразу учитывала
  новые названия/длины).

### Добавление объектов и связей

В режиме правки в шапке появляются ещё две кнопки:

- **«➕ Объект»** → кликните место на карте → форма: тип (СНП/АТС/OLT/ATN/
  NetEngine/муфта), подтип (для СНП — технология, для оборудования —
  существующий/по проекту), название, район, подключения. «Создать» →
  объект появляется на карте и сохраняется в JSON (id генерирует сервер).
- **«🔗 Связь»** → кликните первый узел, затем второй → форма: тип ВОЛС и
  плановая длина. Дубликат связи (та же пара узлов, тот же тип) сервер
  отклонит с 409. Esc отменяет режим на любом шаге.
- **«〰️ Линия OLT/АТС»** → кликните первый узел (обычно OLT или АТС), затем
  второй → форма: голубая PON-ветка или зелёный аплинк. См. ниже.
- **«🗑 Удалить линии OLT/АТС»** → удаляет ВЕСЬ этот слой сразу и насовсем. См. ниже.
- **«🗑 Удалить»** в панели объекта/связи (с подтверждением). Удаление узла
  каскадно снимает все его связи.

После любой операции сервер пересчитывает все `meta.counts` (число узлов по
типам, связей по типам, `totalKm`/`plannedKm`) — проверено, что пересчёт
совпадает с исходными значениями файла, «дрейфа» нет.

### Извилистые линии OLT/АТС — правка картинки

Извилистые PON/аплинк-линии **не несут никакой логики**: в километры, прогресс,
привязку отчётов и маршруты они не входят вообще — это только отображение, как
на чертеже. Фронт **не достраивает их сам**: раньше он восстанавливал линии по
топологии (ближайшая OLT по Дейкстре) и рисовал связи, которых на чертеже нет —
эта автодостройка убрана. Рисуется ровно то, что нарисовано руками:

- **добавить** — «〰️ Линия OLT/АТС», два клика по узлам, выбор цвета/типа;
- **убрать одну** — клик по самой линии на карте либо по пункту `〰️ …` в панели
  узла → «🗑 Убрать линию»;
- **удалить все сразу** — «🗑 Удалить линии OLT/АТС» (с подтверждением): линии
  удаляются из файла. Удаление **окончательное** — кнопки «вернуть» нет: слой
  остаётся пустым, и дальше вы наполняете его заново кнопкой «〰️ Линия OLT/АТС».

Чекбокс **«PON/аплинки»** — это личный фильтр отображения в браузере, он ничего
не сохраняет и линии не удаляет. Кнопка «🗑 Удалить линии OLT/АТС» — правка
графа: она пишется в JSON и видна всем.

В JSON это отдельные поля, `nodes`/`edges` не трогаются:

```json
"serviceLinks": [ { "id": "S1a2b3c", "from": "N0101", "to": "N0207", "kind": "pon" } ]
```

`serviceLinks` — нарисованные руками линии, единственный источник этого слоя.
Удаление узла снимает его линии каскадом. Поля времён автодостройки
(`serviceLinksHidden`, `serviceLinksAuto`, `serviceLinksOff`) больше не читаются
и не пишутся: в старых файлах они просто лежат, а «🗑 Удалить линии OLT/АТС»
заодно вычищает их из файла.

Редактирование работает только когда страница открыта через `server.py`
(двойной клик по index.html — просмотр без сохранения: кнопка покажет
«нет связи с server.py»). Разрешённые поля жёстко ограничены белым списком
(узел: `name`, `connectionCount`; ребро: `lengthKm`) — остальное в JSON
с фронта менять нельзя. Запись атомарная (tmp-файл + replace), правки
сериализуются, так что одновременные сохранения друг друга не портят.
API: `POST /api/graph/edit`, `/api/graph/add-node`, `/api/graph/add-edge`,
`/api/graph/delete`, `/api/graph/add-service-link`, `/api/graph/delete-service-link`,
`/api/graph/clear-service-links`.

## URL-параметры

`?district=Байзакский` — открыть сразу район;
`?theme=light|dark` — принудительная тема; `?edit=1` — сразу включить режим
правки. Пример: `index.html?district=Жуалинский&edit=1`.
