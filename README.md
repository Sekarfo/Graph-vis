# Визуализация графа ВОЛС — по областям

Интерактивный вьюер плана строительства: `index.html` + `graph-app.js`.
Графов несколько (по областям), каждый — отдельный файл `regions/<slug>.json`;
какой открыт — решает URL-параметр `?graph=<slug>`.

**Работаете над своей областью или правите чужую?** → [CONTRIBUTING.md](CONTRIBUTING.md)
— как несколько человек добавляют/правят области параллельно без конфликтов
в git, локальный вьюер с правками, что коммитить и как деплой подхватывает
новые области сам.

## Несколько графов (областей)

Список графов сервер строит **сам**, сканируя `regions/*.json`
(`discover_graphs()` в `server.py`) — никакого реестра в коде нет, у каждого
файла есть собственный блок `meta.registry {slug, title, idPrefix}`:

| slug | файл | что внутри |
|------|------|-----------|
| `zhambyl` (дефолт) | `regions/zhambyl.json` | Жамбылская область (514 узлов, 522 линии) |
| `almaty-zhetysu` | `regions/almaty-zhetysu.json` | Алматинская область + Жетісу (1082 узла, 967 линий, 20 районов; оцифровано с того же чертежа) |

- **Фронт**: селектор области в шапке (появляется, когда сервер отдаёт
  `GET /api/graphs` и графов ≥ 2); прямые ссылки — `index.html?graph=almaty-zhetysu`.
  Без параметра открывается жамбылский граф — все старые ссылки живы.
- **API**: каждый эндпоинт (`/api/progress`, все `/api/graph/*`) принимает
  `?graph=<slug>`; без него работает дефолтный граф. Файл графа —
  `GET /regions/<slug>.json` (легаси-путь `/zhambyl-graph.json` сохранён —
  им пользуется бот, см. `app/config.py: graph_path` в основном репозитории).
- **Правки** независимы по графам (свой файл, свой лок, свой кэш прогресса);
  id новых узлов получают префикс графа (`N…` — Жамбыл, `A…` — Алматинская+Жетісу),
  чтобы привязка `graph_from_node`/`graph_to_node` от бота не могла указать
  на узел чужого графа. `idPrefix` каждой области обязан быть уникален —
  `scripts/validate_region.py` проверяет это перед коммитом.
- **Прогресс**: push от бота один на всех (полный снимок строк);
  жамбылский граф получает все строки (как раньше), остальные — только строки
  своей области (по привязке от бота либо совместимости района отчёта с
  районами графа — иначе сёла-тёзки утаскивали бы км в чужую область).
- **Добавить область**: `python scripts/new_region.py <slug> "<Название>"` —
  создаёт `regions/<slug>.json` с уникальным `idPrefix` автоматически. Дальше
  файл сразу подхватывается сервером, `Dockerfile` копирует всю папку
  `regions/` целиком — деплой ничего не нужно править. Подробности —
  [CONTRIBUTING.md](CONTRIBUTING.md).
- **Fallback для file://**: `regions/<slug>.fallback.js`
  (`window.GRAPH_DATA_BY_SLUG[slug]`), подключается фронтом динамически,
  одинаково для всех графов включая дефолтный.

### Оцифровка `regions/almaty-zhetysu.json` — как и что проверено

Данные извлечены векторной экстракцией из PDF (PyMuPDF: подписи со
координатами + пути ВОЛС с цветом/пунктиром/толщиной — та же классификация
цветов, что в легенде чертежа), не «на глаз». Проверено:

- **Районы** — 20 районов через flood-fill отсеков между границами
  (штрих-пунктирные барьеры чертежа): 0 утечек между отсеками, 0 узлов вне
  отсеков после калибровки. Точечно сверено по PDF: Хоргос/Чунджа/Нарынкол/
  Каратал и др. — район/область совпадают.
- **Внешние связи** (5 шт., переход в Жамбылскую область) сверены по km
  с зеркальными записями в `regions/zhambyl.json` — совпадают (например, 93.4 км
  Каншенгель↔Аксуйек с обеих сторон).
- **Визуальная сверка** нескольких районов (растр PDF vs рендер JSON) —
  топология, названия и км-подписи совпадают.

Известные пробелы (не критично — правятся через «✏️ Правка» в вьюере, как
любые данные графа):

- ~15% рёбер новой области (149 из 967) не получили `lengthKm` — подпись
  «N км» на чертеже стоит слишком далеко от линии для автоматической
  привязки. Такое ребро просто рисуется без дроби «X/Y км», как и 9 таких
  рёбер в исходном жамбылском графе.
- 11 узлов (АТС/ATN) без имени — на самом чертеже эти значки не подписаны
  отдельно (либо подпись однозначно относится к соседнему объекту).
- В отчёте экстракции (`build_edges.py` в scratch) остаётся ~37 «висячих»
  обрывов линий — на практике это дублирующиеся короткие хвосты одного и того
  же соединения на чертеже (проверено точечно: сама связь между узлами при
  этом уже создана из другого сегмента той же линии), не потерянная топология.

## Как открыть

**Вариант 1 (просто):** двойной клик по `index.html` — страница возьмёт данные из
`regions/<slug>.fallback.js` (fallback для `file://`; только просмотр, без правки).

**Вариант 2 (сервер, нужен для правки):**

```bash
cd graph-vis
pip install -r requirements.txt
uvicorn server:app --reload
# → http://localhost:8000
```

Если `regions/<slug>.json` обновился не через UI (правили руками/скриптом) —
перегенерировать fallback:

```bash
python scripts/build_fallback.py               # все regions/*.json
python scripts/build_fallback.py regions/zhambyl.json   # один файл
```

## Возможности

- **Пан/зум** — перетаскивание мышью, колесо, двойной клик; кнопка «Вписать».
- **Клик по узлу** — панель с деталями (район, подключения, objectId) и списком
  всех связей с длинами и прогрессом; клик по связи ведёт к соседнему узлу.
- **Фильтры** — район, муфты вкл/выкл, существующие/плановые ВОЛС.
- **PON/аплинки** — извилистые линии как на чертеже: голубые (#00B0F0) —
  PON-ветки от OLT к обслуживаемым СНП, зелёные (#00B050) — аплинк от
  существующей ATN к OLT. Связи восстанавливаются по топологии (ближайшая
  OLT по графу, Дейкстра), отключаются галочкой «PON/аплинки». Логики не несут
  (в км и прогресс не входят) и правятся руками — см. «Извилистые линии OLT/АТС».
- **Поиск с нечётким сопоставлением каз/рус** (см. ниже).
- **Тема** — светлая/тёмная (кнопка ◐ или системная).

## Прогресс строительства (линия = прогресс-бар)

Выполненная часть сегмента рисуется сплошной зелёной линией поверх плановой
(пунктирной), с подписью `1.5/3 км`, заливка идёт со стороны, откуда строят
(`fillFrom`). Источники прогресса, по приоритету:

1. **`GET /api/progress`** — живые данные из PostgreSQL (см. «Живое обновление»);
   фронт поллит раз в 30 сек и перерисовывает при изменении `version`.
2. Файл `progress.json` рядом с `index.html` (fallback без БД, формат тот же):

```json
{
  "edges": { "E0000": { "doneKm": 2.5 }, "E0281": { "progress": 0.4 } }
}
```

3. Поля `doneKm` / `progress` прямо на ребре в `regions/<slug>.json`.

Галочка **«демо прогресса»** показывает, как это будет выглядеть (случайные доли
на плановых линиях; реальные данные она не подменяет).

## Живое обновление (server.py)

Браузер не умеет ходить в Postgres напрямую, поэтому между данными и фронтом
стоит маленький API (`server.py`, FastAPI). Прогресс он берёт из двух
источников, по приоритету:

**1. Push от бота (основной).** Postgres живёт на сервере бота, который не
принимает входящих соединений — задеплоенный на Railway вьюер до БД не
достучится. Поэтому бот сам присылает полный снимок строк прогресса на
`POST /api/progress/push` (заголовок `X-Push-Key`, общий секрет): сразу после
подтверждения или правки отчёта плюс фоновым циклом раз в 5 минут (см.
`app/services/graphvis.py` в репозитории бота). Снимок хранится в памяти и в
`DATA_DIR/progress-rows.json` — с volume на Railway переживает рестарты.

```
Telegram-бот ──▶ PostgreSQL (сервер бота, только localhost)
      │
      └── POST /api/progress/push ──▶ server.py (Railway: вьюер + /api/progress)
                                             ▲
                                   браузер: поллинг раз в 30 сек
```

**2. Прямой SQL из PostgreSQL** — как раньше: если задан `DATABASE_URL` и БД
достижима (запуск на той же машине, где база). Используется, только пока не
пришёл ни один push.

Запуск:

```bash
cd graph-vis
pip install -r requirements.txt
export PUSH_KEY=<секрет, тот же что GRAPHVIS_PUSH_KEY у бота>
# export DATABASE_URL=postgresql://user:pass@host:5432/db  # только для запуска рядом с БД
uvicorn server:app --host 0.0.0.0 --port 8080
# → http://<хост>:8080  (вьюер) и /api/progress, /api/health
```

Либо Docker: `docker build -t graph-viewer . && docker run -p 8080:8080 -e DATABASE_URL=... graph-viewer`

### Деплой на Railway

Репозиторий содержит `Dockerfile` и `railway.json` — Railway подхватывает их
автоматически, отдельной настройки билда не нужно.

1. **New Project → Deploy from GitHub repo** → выбрать `Sekarfo/Graph-vis`.
2. **Variables**: `PUSH_KEY` — общий секрет с ботом (у него это
   `GRAPHVIS_PUSH_KEY`; без переменной действует дефолт из кода — для боевого
   деплоя задайте свой); `DATABASE_URL` больше не нужен (БД на сервере бота
   недоступна снаружи — данные присылает сам бот, см. выше); опционально
   `EDIT_PASSWORD` и/или `READ_ONLY=1` для публичной ссылки. Порт слушать
   не нужно задавать — Railway сам прокидывает `PORT`, сервер его подхватывает.
3. **Volume** (обязательно, если пользуетесь правкой графа через фронт):
   Settings → Volumes → добавить том с mount path `/data`, затем задать
   переменную `DATA_DIR=/data`. Без этого шага правки графа (кнопка
   «✏️ Правка») будут пропадать при каждом следующем деплое — контейнер
   стартует с нуля из образа. При первом запуске том пустой, сервер сам
   скопирует туда все `regions/*.json` из образа (см. `discover_graphs()`
   в `server.py`); дальше все правки читаются/пишутся уже из тома, и именно
   их отдаёт `/regions/<slug>.json` — а не файлы из образа (уже существующие
   в томе файлы не перезаписываются, так что новый деплой с новыми областями
   в `regions/` докопирует только недостающее). Присланный ботом
   снимок прогресса (`progress-rows.json`) тоже лежит в томе — после
   передеплоя прогресс виден сразу, не дожидаясь следующего push (бот в любом
   случае повторяет его раз в 5 минут).
4. Healthcheck в `railway.json` указывает на `/` (всегда 200), а не на
   `/api/health` — тот честно отвечает 503, пока не настроен `DATABASE_URL`,
   и Railway бы считал деплой нездоровым до подключения БД.

Защита правки для публичных ссылок (тоннель и т.п. — на `/api/graph/*` иначе
нет вообще никакой авторизации): `EDIT_PASSWORD=<пароль>` — при первом же 401
от `/api/graph/*` фронт спросит пароль, обменяет его на токен сессии через
`POST /api/graph/login` (12 часов, с блокировкой после 5 неверных попыток) и
дальше будет слать токен заголовком `X-Edit-Token`; `READ_ONLY=1` — правка
отключена совсем, даже с верным паролем. Ни один флаг не задан — правка
открыта всем (локальный/доверенный запуск).

Как считается прогресс (`progress_core.py`, тестируется без БД):

1. Берутся отчёты `work_reports` (кроме `rejected`) с километровыми показателями;
   приоритет: задувка ВОК → микротрубка ПЭТ → траншея.
2. «Откуда» (`direction_from`) и «куда» (`settlement_name`) резолвятся нечётким
   поиском по узлам графа (порог 60/100, бонусы за СНП и совпадение района).
3. Строится кратчайший маршрут по графу, км укладываются по рёбрам
   последовательно от «откуда» — как физически идёт стройка.
4. Если «откуда» не указано, а у села ровно одна плановая линия — км ложатся на неё.
5. Всё, что не привязалось (село не найдено, маршрута нет, факт превысил план),
   попадает в `unmatched` ответа API — фронт показывает счётчик «без привязки»
   и пишет детали в консоль браузера.

«Новая запись появилась» отслеживается дёшево: API при каждом запросе сверяет
`max(id)`/`count` по таблицам (миллисекунды) и пересчитывает привязку только
если данные изменились; ответ кэшируется на 10 сек, так что хоть 50 открытых
вкладок нагрузки на Postgres не создадут.

## Сопоставление названий сёл (каз ↔ рус)

Поиск устойчив к разнице алфавитов и опечаткам: «Костобе» находит «Қостөбе»,
«Женис» → «Жеңіс», «Ауликоль» → «Әулиекөл». Алгоритм (`window.snpMatcher` в
`graph-app.js`):

1. нижний регистр, отбрасывание префиксов «с.», «ст.», «рзд.», «АТС», «СНП» и т.п.;
2. транслитерация казахских букв к русским: ә→а, ғ→г, қ→к, ң→н, ө→о, ұ/ү→у, і→и, һ→х;
3. точное совпадение / префикс / вхождение, иначе расстояние Левенштейна
   (порог схожести ~45/100).

Тот же алгоритм нужно будет портировать в Python-часть бота, когда репорты
начнут привязываться к рёбрам графа автоматически.

## Редактирование графа с фронта (✏️ Правка)

Кнопка **«✏️ Правка»** в шапке включает режим редактирования:

- клик по **селу/объекту** → в панели справа появляются поля «Название» и
  (для СНП) «Подключений по плану»;
- клик по **линии** → поле «Плановая длина, км» (пустое = длина не задана);
- «💾 Сохранить» → изменение уходит `POST /api/graph/edit` и **автоматически
  сохраняется в `regions/<slug>.json`** (плюс синхронно перегенерируется
  `regions/<slug>.fallback.js`, пересчитываются итоги `totalKm`/`plannedKm`
  и сбрасывается кэш `/api/progress`, чтобы привязка отчётов сразу учитывала
  новые названия/длины).

### Добавление объектов и связей

В режиме правки в шапке появляются ещё две кнопки:

- **«➕ Объект»** → кликните место на карте → форма: тип (СНП/АТС/OLT/ATN/
  NetEngine/муфта), подтип (для СНП — технология, для оборудования —
  существующий/по проекту), название, район, подключения. «Создать» →
  объект появляется на карте и сохраняется в JSON (id генерирует сервер).
- **«🔗 Связь»** → кликните первый узел, затем второй → форма: тип ВОЛС и
  плановая длина. Дубликат связи (та же пара узлов, тот же тип) сервер
  отклонит с 409. Esc отменяет режим на любом шаге.
- **«〰️ Линия OLT/АТС»** → кликните первый узел (обычно OLT или АТС), затем
  второй → форма: голубая PON-ветка или зелёный аплинк. См. ниже.
- **«🗑 Удалить»** в панели объекта/связи (с подтверждением). Удаление узла
  каскадно снимает все его связи.

После любой операции сервер пересчитывает все `meta.counts` (число узлов по
типам, связей по типам, `totalKm`/`plannedKm`) — проверено, что пересчёт
совпадает с исходными значениями файла, «дрейфа» нет.

### Извилистые линии OLT/АТС — правка картинки

Извилистые PON/аплинк-линии **не несут никакой логики**: в километры, прогресс,
привязку отчётов и маршруты они не входят вообще — это только отображение, как
на чертеже. По умолчанию фронт достраивает их сам по топологии, а руками эту
картинку можно поправить:

- **добавить** — «〰️ Линия OLT/АТС», два клика по узлам, выбор цвета/типа;
- **убрать** — клик по самой линии на карте либо по пункту `〰️ …` в панели
  узла → «🗑 Убрать линию». Работает одинаково для авто- и ручных линий.

В JSON это отдельные поля, `nodes`/`edges` не трогаются:

```json
"serviceLinks":       [ { "id": "S1a2b3c", "from": "N0101", "to": "N0207", "kind": "pon" } ],
"serviceLinksHidden": [ "N0101|N0250" ]
```

`serviceLinks` — нарисованные руками линии, `serviceLinksHidden` — пары узлов
(id отсортированы), на которых авто-линия погашена. Добавление кладёт пару и в
`serviceLinksHidden` тоже, чтобы ручная линия не задвоилась с авто. Удаление
узла снимает его линии каскадом.

Редактирование работает только когда страница открыта через `server.py`
(двойной клик по index.html — просмотр без сохранения: кнопка покажет
«нет связи с server.py»). Разрешённые поля жёстко ограничены белым списком
(узел: `name`, `connectionCount`; ребро: `lengthKm`) — остальное в JSON
с фронта менять нельзя. Запись атомарная (tmp-файл + replace), правки
сериализуются, так что одновременные сохранения друг друга не портят.
API: `POST /api/graph/edit`, `/api/graph/add-node`, `/api/graph/add-edge`,
`/api/graph/delete`, `/api/graph/add-service-link`, `/api/graph/delete-service-link`.

## URL-параметры

`?district=Байзакский` — открыть сразу район; `?demo=1` — демо прогресса;
`?theme=light|dark` — принудительная тема; `?edit=1` — сразу включить режим
правки. Пример: `index.html?district=Жуалинский&edit=1`.
